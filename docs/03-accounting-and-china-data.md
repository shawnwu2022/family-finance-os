# 账务口径与中国数据接入

## 1. ezBookkeeping 作为交易事实源

选择原因：当前官方提供移动 UI/PWA、HTTP API、AI 图片识别/Web Share Target、对账、支付宝/微信/京东账单导入。V1 不重复实现这些成熟能力。

## 2. 推荐账户模型

示例：

```text
资产
├─ 现金
├─ 银行活期
├─ 支付宝余额
├─ 微信零钱
├─ 存款/低风险现金管理
└─ 投资账户（V1 只记录汇总价值）

负债
├─ 信用卡
├─ 消费贷
├─ 车贷
└─ 房贷
```

### 信用卡原则

- 刷卡消费：Expense，来源为信用卡账户；
- 信用卡还款：Transfer，从银行资产账户到信用卡负债账户；
- 不能把“刷卡消费 + 信用卡还款”都算支出。

## 3. 分类原则

建议维持稳定的一级分类，二级分类用于分析。不要为了每个商户创建分类。商户归一化与分类是两个维度。

最低语义组：
- 住房；
- 食品/餐饮；
- 交通；
- 医疗；
- 教育；
- 赡养；
- 保险；
- 通讯/水电；
- 娱乐；
- 购物；
- 旅行；
- 数码；
- 其他必要；
- 其他可选。

## 4. 中国账单导入

官方已支持支付宝 App/Web、微信支付、京东金融。银行/信用卡优先使用官方导出的 CSV/Excel/OFX（如果银行提供），通过 ezBookkeeping 映射导入。

不建议 V1 做：
- 保存网银密码；
- 自动化登录个人银行；
- 抓短信验证码；
- 逆向支付平台私有 API。

## 5. 截图记账

截图识别后的交易必须由用户确认。识别出多个金额时，UI 要求明确“实付金额”。

月底正式账单导入后，先通过 ezBookkeeping 对账能力和人工抽查处理重复。V1.1 再建立自动匹配系统。

## 6. 退款与报销

项目必须在实现时选定并测试统一口径：
- 消费退款优先关联原分类，减少净支出；
- 公司报销款不能默认算工资收入；
- 自己账户间转账不算收入/支出；
- 借款到账不是经营/工资收入；
- 归还借款不是普通消费。

## 7. 数据质量标签

Finance Core 的每个摘要至少包含：

```text
as_of
last_ledger_sync_at
reconciled_through
missing_account_count
unknown_category_amount
quality_level: good | partial | stale
```

AI 必须把 `partial/stale` 传递给用户。
